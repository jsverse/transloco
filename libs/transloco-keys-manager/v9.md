# Transloco Keys Manager V9

Candidate breaking changes for the next major.

Items 1 and 2 share a root cause with [#258](https://github.com/jsverse/transloco-keys-manager/pull/258) but
were deliberately left out of it, because each changes behaviour beyond the bug that PR fixes. The guiding
principle for both: **`find` is the source of truth for extra-key semantics.** The extract pipeline should
agree with the keys detective, not carry its own definition of what counts as an extra key.

Items 3 and 4 come out of [#217](https://github.com/jsverse/transloco-keys-manager/issues/217) and belong
together: one command-line option is either supported by the command you invoked or it is not, and today
nothing enforces that on either input surface. Item 3 is the escalation half of a two-stage deprecation for
the CLI (warn in 8.x, error here); item 4 does the same for the config file, and is what makes the hard error
in item 3 clean rather than a provenance workaround.

Item 5 closes the last of the four `find` gaps found while investigating #217.

---

## 1. Normalize the translation shape before merging

### Current behaviour

`resolveTranslation` merges the file on disk into the extracted keys:

```ts
// src/keys-builder/utils/create-translation.ts
return mergeDeep({}, translation, currentTranslation);
```

The two sides can disagree on shape:

- `currentTranslation` is read from disk as-is — `get-current-translation.ts` → `parseJson` → `fs.readJsonSync`,
  with no flattening. It keeps whatever shape the file happens to have.
- `translation` (the extracted keys) is always flat, unless `unflat` is on, in which case `createJson`
  unflattens it just before the merge.

When the file is nested and `unflat` is falsy (the default), the merge emits both spellings of every key.
Given a template using `used.key` and this `en.json`:

```json
{
  "used": { "key": "translated value" },
  "totally": { "extra": "stale" }
}
```

a plain `extract` returns:

```json
{
  "used.key": "Missing value for 'used.key'",
  "used": { "key": "translated value" },
  "totally": { "extra": "stale" }
}
```

No data is lost, but the file now carries a duplicated, half-flat/half-nested structure. This happens with
or without `--remove-extra-keys`, so #258 does not affect it in either direction.

### Proposal

Normalize `currentTranslation` to the configured output shape before comparing or merging — flatten it when
`unflat` is falsy, unflatten it when `unflat` is on. One consistent shape at the boundary removes the
duplication and lets a single code path serve both the merge and the extra-key check.

### Why it is breaking

Output changes for every user whose file shape does not match their `unflat` setting, including those who
never pass `--remove-extra-keys`. The next `extract` after upgrading will rewrite those files into one
consistent shape — a large but one-time diff.

## 2. Stop deleting `*.comment` keys with `--remove-extra-keys`

### Current behaviour

The keys detective deliberately excludes `*.comment` keys from the extra list, to support the convention of
keeping a translator note alongside a key:

```ts
// src/keys-detective/compare-keys-to-files.ts
const isComment = diff.path!.join('.').endsWith('.comment');
if (!isComment) {
  diffsPerLang[langPath].extra.push(diff);
}
```

`removeExtraKeys` has no such exclusion, so the two commands disagree. Given:

```json
{
  "used.key": "translated value",
  "used.key.comment": "note for translators",
  "totally.extra": "stale"
}
```

- `find --emit-error-on-extra-keys` reports only `totally.extra`.
- `extract --remove-extra-keys` removes `totally.extra` **and** `used.key.comment`.

### Proposal

Apply the same exclusion in the extract pipeline, so `find` remains the single definition of what counts as
an extra key.

### Why it is breaking

`--remove-extra-keys` will stop deleting keys it currently deletes. Anyone relying on it to prune
`*.comment` keys gets different output.

### Open question

The detective's check is a suffix heuristic, not a real convention. `endsWith('.comment')` also protects a
genuine, in-use key that merely happens to be named that way — the repo's own `comments` fixture contains
`from.comment` and `early.exit.comment.key`. Before propagating the heuristic to a second place, it is worth
deciding whether translator notes deserve an explicit mechanism instead of a magic suffix.

## 3. Hard-error on CLI flags the command does not support

> **Status: deferred to v10.** v9 ships the 8.x warning unchanged - unsupported flags are still
> accepted-and-ignored and the run exits zero. The non-zero exit lands in v10. The proposal below
> stands as written; only the target release moved.

### Current behaviour

`optionDefinitions` is one flat list shared by both commands, and `src/index.ts` parses it once before
dispatching:

```ts
// src/index.ts
const config = commandLineArgs(optionDefinitions, { camelCase: true, argv });
// ...
if (resolvedConfig.command === 'extract') {
  buildTranslationFiles(resolvedConfig);
} else if (resolvedConfig.command === 'find') {
  findMissingKeys(resolvedConfig);
}
```

There is no per-command schema, so every flag parses for every command and the unsupported ones are silently
ignored. `--emit-error-on-extra-keys` (`cli-options.ts`, alias `-e`) has been accepted-and-ignored by
`extract` since [#39](https://github.com/jsverse/transloco-keys-manager/pull/39) (2020) — only the keys
detective ever reads it. Same for `--add-missing-keys`; `--remove-extra-keys`, `--default-value` and
`--output` are the mirror image, extract-only flags accepted by `find`.

That silence is what [#217](https://github.com/jsverse/transloco-keys-manager/issues/217) reported: users
reasonably read `--remove-extra-keys` and `--emit-error-on-extra-keys` as a pair, pass both to `extract`, and
get no feedback that half of it does nothing.

### Proposal

Split `optionDefinitions` into per-command schemas and reject flags the invoked command does not support,
with a non-zero exit — the convention in every comparable tool:

| tool   | wrong-subcommand / unknown flag | result                                            |
| ------ | ------------------------------- | ------------------------------------------------- |
| git    | `git push --amend`              | `error: unknown option 'amend'`                   |
| docker | `docker ps --detach`            | `unknown flag: --detach`                          |
| cargo  | `cargo build --frobnicate`      | `error: unexpected argument`                      |
| tsc    | `tsc --frobnicate`              | `error TS5023`                                    |
| eslint | `eslint --frobnicate`           | `Invalid option` + did-you-mean                   |
| npm    | `npm ls --frobnicate`           | `npm warn Unknown cli config …` (lenient outlier) |

Note that git treats a known-but-wrong-subcommand flag exactly like an unknown one, because its parsers are
per-subcommand; truly global flags (`-C`, `--no-pager`) must precede the subcommand. That is the shape TKM
should end up with.

### The constraint that shapes this: provenance

The error must key on **how the value arrived**, not just on whether the command supports it:

| source                               | v9 behaviour                                                     |
| ------------------------------------ | ---------------------------------------------------------------- |
| Explicit CLI flag                    | Hard error, non-zero exit. The user typed it for _this_ command. |
| Shared `transloco.config.js` / `.ts` | Silent (`devlog` at most). The user did nothing wrong.           |

One config file legitimately serves both commands, and `TranslocoGlobalConfig['keysManager']` from
`@jsverse/transloco-utils` explicitly types `emitErrorOnExtraKeys` — so a config file with that key set is
correct for `find` and harmlessly inert for `extract`. Erroring on it would break every `extract` run of a
correctly configured project. Warning on it at normal verbosity is nearly as bad: it would nag on every run
and train people to ignore TKM's output.

Provenance is already available for free, because `command-line-args` omits unpassed Boolean flags from its
result entirely — `'emitErrorOnExtraKeys' in commandLineArgs(optionDefinitions, { argv: ['--sort'] })` is
`false`. Inspecting the raw parse result in `src/index.ts`, before `resolveConfig` merges in defaults and the
file config, distinguishes the two sources with no extra plumbing.

### Why it is breaking

Runs that pass an unsupported flag on the CLI go from exit 0 to a non-zero exit. That includes setups doing
nothing harmful, like a shared CI template feeding the same flag list to both commands, or
`tkm extract -e && tkm find -e` in one npm script.

### Prerequisite in 8.x

Ship the warning first: `extract` should warn on stderr when an unsupported flag was passed **on the CLI**,
leaving the exit code alone. This is npm's staged path — `npm warn Unknown cli config "--frobnicate". This
will stop working in the next major version of npm.` — and it matters more than usual here, since 8.x has
already moved exit codes twice ([#257](https://github.com/jsverse/transloco-keys-manager/pull/257),
[#258](https://github.com/jsverse/transloco-keys-manager/pull/258)). Without that warning release, this
change lands as an unannounced red build on upgrade.

> Shipped: the 8.x warning exists — `warnUnsupportedOptions` in `src/utils/warn-unsupported-options.ts`,
> driven by the `commandSpecificOptions` map in `src/cli-options.ts`.

## 4. Give the config file per-command sections

### Current behaviour

`keysManager` in `TranslocoGlobalConfig` (`@jsverse/transloco-utils`, currently 8.4.0) is a single flat bag
with no notion of which command reads what:

```ts
keysManager?: {
  input?: string | string[];
  output?: string;              // extract only
  fileFormat?: 'json' | 'pot';
  marker?: string;
  addMissingKeys?: boolean;     // find only
  emitErrorOnExtraKeys?: boolean; // find only
  replace?: boolean;            // extract only
  defaultValue?: string | undefined;
  unflat?: boolean;
  sort?: boolean;
};
```

Two consequences, both verified against 8.4.0:

- **Command-specific keys sit next to shared ones with nothing marking them.** `emitErrorOnExtraKeys` is inert
  for `extract` and `output` is inert for `find`, but the type invites both into the same object. This is the
  exact reason item 3 has to fall back on CLI provenance: the file cannot express intent, so a key set there
  cannot be judged wrong.
- **The type is already out of sync with the runtime.** `removeExtraKeys` is missing from it, yet setting it
  in `transloco.config.js` does prune keys — `flatFileConfig` spreads `keysManager` wholesale
  (`src/utils/resolve-config.ts:74-76`), so any key present at runtime wins regardless of the type. A TS user
  writing the key that actually works gets an excess-property error. `translationsPath` is the mirror image:
  supported by the CLI as `--translations-path`, but only settable in the file through top-level
  `rootTranslationsPath`.

### Proposal

Restructure `keysManager` so the shape itself encodes what applies where:

```ts
keysManager?: {
  // read by both commands
  input?: string | string[];
  langs?: string[];
  fileFormat?: 'json' | 'pot';
  marker?: string;
  defaultValue?: string;
  sort?: boolean;
  unflat?: boolean;
  translationsPath?: string;

  extract?: { output?: string; replace?: boolean; removeExtraKeys?: boolean };
  find?: { addMissingKeys?: boolean; emitErrorOnExtraKeys?: boolean };
};
```

Then a misplaced key is unambiguous on both surfaces — `find.emitErrorOnExtraKeys` under `extract` is an
error no matter how it arrived — and item 3's hard error stops being provenance-dependent. It also fixes the
drift: `removeExtraKeys` and `translationsPath` get typed, and the shared block becomes the single answer to
"does this apply to both?" instead of the stale comment block in `src/config.ts:52-73`.

Note which options are genuinely shared, because two of them read as extractor-only and are not: `find` runs
the same extraction pipeline as `extract`, so `defaultValue` supplies the value `--add-missing-keys` writes
(via `addKey` in `src/keys-builder/add-key.ts`), and `sort` orders that write (`writeFile` → `stringify` →
`getConfig().sort` in `src/utils/object.utils.ts`). Both are verified reachable from `find`.

### Cross-repo dependency

`TranslocoGlobalConfig` is owned by **`@jsverse/transloco-utils`**, not this repo, so this needs a coordinated
major there and cannot land from TKM alone. Sequencing matters: transloco-utils has to accept the new shape
(reading both, deprecating the flat one) before TKM can require it.

### Why it is breaking

Every existing `transloco.config.js` with `output`, `replace`, `removeExtraKeys`, `addMissingKeys` or
`emitErrorOnExtraKeys` at the top of `keysManager` has to move those keys into a section. Ship a shim that
reads the flat shape, warns, and maps it forward, so the migration is mechanical rather than a hard break on
upgrade.

## 5. Report extra keys for scopes mapped in `scopePathMap` but absent from the code

### Current behaviour

`compareKeysToFiles` walks `scopePathMap` and silently drops any scope the extractor found no keys for:

```ts
// src/keys-detective/compare-keys-to-files.ts:60-63
const scopePaths = getGlobalConfig().scopePathMap || {};
for (const [scope, path] of Object.entries(scopePaths)) {
  const keys = scopeToKeys[scope];
  if (keys) {
```

`scopeToKeys` is built from scope declarations discovered in code (`updateScopesMap`). So when a scope is
mapped in `scopePathMap` but no code declares it any more — the feature was deleted, the mapping was not —
its translation files are never opened. Every key in them is unreported, and `find --emit-error-on-extra-keys`
exits 0 on a directory that is now entirely dead. The failure is silent in the worst way: the mapping's whole
purpose is to bring those files under the detective, and the detective skips them.

### Proposal

Treat a mapped scope with no code-declared keys as a scope with **zero** keys rather than as absent, so its
files are read and every key in them is reported as extra. There is no ambiguity to weigh here: the user
explicitly declared the scope-to-path mapping, so an absent entry in `scopeToKeys` means nothing in the code
declares it.

### Why it is breaking

`find --emit-error-on-extra-keys` flips from exit 0 to exit 2 for any project carrying a stale mapping, and
the extra-key count can be the entire contents of a directory. Same staging as item 3 applies: warn in 8.x
naming the skipped scope, error here.

### Out of scope: the sibling skip

The second skip site (`:88-89`, iterating globbed translation directories) looks identical but is not. There
the scope name is inferred from a directory name, so `i18n/backup/en.json` is indistinguishable from a
deleted scope's leftovers — reporting every key under it as extra would produce false positives on any
unrelated folder sitting in the translations path. That one needs a real answer to how scopes are configured
before it can change; a warning is the only honest response until then. **A tracking issue for it still needs
to be filed.**
